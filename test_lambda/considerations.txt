Important clarification: these two things you asked about aren't quite the same kind of relationship.
API Gateway → Lambda (trigger): there's no separate "trigger" resource. It's just two pieces already in your existing files — aws_api_gateway_integration with type = "AWS_PROXY" and uri = var.lambda_invoke_arn (the wiring), plus aws_lambda_permission with principal = "apigateway.amazonaws.com" (the permission). You already have both in apigateway_module.tf and lambda.tf. Nothing more to add — just make sure the root module passes module.lambda.lambda_invoke_arn and module.lambda.lambda_function_name into the API Gateway module.
Lambda → SQS: this is not a Lambda "destination" in Terraform's sense. Destinations (aws_lambda_function_event_invoke_config) only apply to async invocations routing success/failure elsewhere — irrelevant here since API Gateway invokes your Lambda synchronously. Your Lambda sends to SQS itself, in code, via sqs.send_message() (already in lambda_handler.py). Terraform's only job is the IAM permission, which you already have in lambda.tf's aws_iam_role_policy "lambda_permissions".
So with your current architecture (API Gateway → Lambda → SQS + S3), the linkage is already complete across the files we've built — I included a root main.tf snippet in the file above showing how the three modules connect.
I also included a commented-out Option B in case you ever want API Gateway to write directly to SQS without invoking Lambda on the write path (lower latency, no cold start), with a separate Lambda consuming the queue via aws_lambda_event_source_mapping. That's a different pattern — only worth it if Lambda's validation logic isn't needed before queuing.
